1. Точность: «Цифровые чернила» (Digital Ink) vs «Плоская картинка» (Raster PNG)
Как работает Mathpix (v3/strokes): Вы отправляете в API векторы и хронологию движений пера/пальца: x, y, t_ms, pressure. Mathpix видит траекторию написания. Если ребенок нарисовал двоеточие, минус или небрежную скобку, по вектору движения легко понять его замысел.

Как работает LLM (Vision): LLM получает растровое изображение (PNG). Она вынуждена угадывать символы по пикселям. В детском рукописном вводе (где символы перекрываются, линии имеют неравномерную толщину, а цифры 1, 7 и / часто сливаются) LLM дает катастрофически высокий процент ложных срабатываний.

Результат: Использование LLM для распознавания математики приведет к тому, что система будет постоянно выдавать ошибку UNRECOGNIZED там, где ребенок написал всё верно, либо (что еще хуже) некорректно зачитывать верный шаг как ошибку ARITHMETIC или SIGN_ON_TRANSFER.

Маршрутизация (Путь А vs Путь Б):

В Пути А (алгебра / уравнения) Mathpix возвращает строгий, готовый для парсера LaTeX (2 x = 11 + 5). Его сразу забирает детерминированный Go-движок (big.Rat), который за < 1 мс выполняет точную математическую проверку.

каким образом детерменированный код в GO вообщ что-то может проверить?

Детерминированный Go-движок проверяет шаги не через «понимание» математики, как это делает человеку или LLM, а через алгебраические трансформации и символьные вычисления (Symbolic Computation / Computer Algebra System, CAS).

Ему не нужно угадывать — он переводит исходное выражение и шаг ребенка в строгое абстрактное синтаксическое дерево (AST) и выполняет их точное сравнение.

Вот 4 основных алгоритмических механизма, как это реализуется в Go:

1. Тождественное упрощение и Канонизация AST (Canonical Representation)
Любое математическое выражение парсится в дерево операторов (AST). Чтобы проверить равенство, Go-движок приводит оба выражения (исходное и шаг ребенка) к каноническому (нормализованному) виду:

Сортировка узлов: Раскрываются скобки, переменные и константы сортируются в лексикографическом порядке (3x+5=5+3x).

Приведение подобных: 2x+4x−1→6x−1.

Канонизация дробей: Все числа переводятся из float в точные рациональные дроби big.Rat (math/big), чтобы избежать ошибок округления (0.3333...→1/3).

Если канонические деревья исходного уравнения и уравнения ребенка совпадают — шаг корректен.

2. Алгебраический символьный символьный анализ (Symbolic CAS)
Для проверки шага в уравнениях Go-движок использует принцип символьной разности или эквивалентности множества решений:

Принцип переноса (A=B⟺A−B=0):

Исходное уравнение: 3x+5=20⟹3x+5−20=0⟹3x−15=0.

Шаг ребенка: 3x=15⟹3x−15=0.

Движок вычитает одно выражение из другого в символьном виде. Если результат упрощается в 0, перенос/преобразование математически верно.

3. Метод случайных подстановок (Evaluative Equivalence / Schwartz-Zippel Lemma)
Если выразить каноническую форму сложно (например, в выражении тригонометрия, степенные функции или сложные многочлены), Go-движок использует детерминированное числовое тестирование:

Берется левая и правая часть шага ученика: f(x) и g(x).

В алгоритм зашит детерминированный генератор псевдослучайных точек (например, x∈{−1.37,0.42,5.89,12.11}).

Вычисляются значения f(x) и g(x) в этих точках с использованием высокоточной арифметики (big.Float / big.Rat).

Если ∀x:∣f(x)−g(x)∣<ϵ, выражения математически эквивалентны с вероятностью 99.99999%.

4. Граф допустимых переходов (Pattern Matching & Rules)
Чтобы не просто сказать «верно/неверно», а определить тип ошибки (например, SIGN_ON_TRANSFER — забыл сменить знак при переносе), Go-движок применяет паттерны ошибок:

Go
type Equation struct {
    Left  ASTNode
    Right ASTNode
}

// Пример проверки переноса слагаемого
func CheckTransferError(prev, current Equation) ErrorType {
    // Движок генерирует гипотетическое "ошибочное" дерево, 
    // где слагаемое перенесли, но НЕ поменяли знак:
    expectedWrong := ApplyRule(prev, RuleTransferWithoutSignChange)
    
    if ASTEqual(current, expectedWrong) {
        return ErrorSignOnTransfer // Забыл поменять знак!
    }
    return ErrorUnknown
}
Почему это работает быстро (< 1–5 мс) на Go?
Нет накладных расходов GIL или JIT: Go компилируется в машинный код, а структуры AST в памяти аллоцируются с минимальным GC-давлением (память под узлы переиспользуется через sync.Pool).

Отсутствие сетевых запросов: В отличие от вызова LLM (где нужно ждать секунду трансляции токенов по HTTP), Go выполняет миллионы операций над деревьями в микросекунды.

Строгая детерминированность: Если ребенок напишет x=5, Go-движок всегда ответит CORRECT и никогда случайно не прогаллюцинирует, что 5 — это не четное число или что знак был перенесен неверно.

       │
       ├───► 1. AST Parser & Linter (Проверка формы записи)
       │        └── Предупреждение / Флаг: "MISSING_PARENTHESES" (Забыл скобки)
       │
       └───► 2. Symbolic CAS Engine (Проверка математической сути)
                └── Вычисление: 1 + (-1) == 0  ➔  Result: CORRECT (Вердикт: ВЕРНО)
1. Вычислительный слой (CAS) — Математика верна
Для математического движка унарный минус имеет более высокий приоритет операций, чем бинарный плюс.
Когда Go строит AST (дерево) для 1 + -1:

Узел 1: Оператор +

Левый потомок: Лист 1

Правый потомок: Узел UnaryMinus → Лист 1

Движок вычисляет 1+(−1)=0 и дает вердикт: «Математический шаг сделан верно». Ребенок не получает ошибочный статус ARITHMETIC_ERROR.

2. Линтер синтаксиса (Style / Notation Rules) — Замечание по оформлению
Парсер Go видит последовательность операторов + и - без разделяющего символа ( (OpenParen).
Движок маркирует этот шаг специальным флагом:

status: "CORRECT"

warning: "FORMAT_MISSING_PARENTHESES"

На основе этого флага система не заставляет ребенка переписывать всё решение, а дает мягкую подсказку (через UI или голос): «Математически всё верно! Но не забудь поставить скобки: 1+(−1), чтобы операторы не сливались».

Почему LLM без Go на этой задаче «поплывет»
Если отдать запись 1 + -1 = 0 на проверку только языковой модели (LLM), возникают две крайности:

Избыточная педантичность (False Negative): LLM может зацепиться за синтаксическую ошибку, посчитать запись невалидной и выдать ребенку: «Неверно, так писать нельзя», сбив его с толку, хотя арифметически он посчитал правильно.

Галлюцинации в правилах (Inconsistency): В 80% случаев LLM закроет глаза на скобки, а в 20% случаев из-за случайной температуры (temperature) или смены контекста начнет снижать баллы.

В чем главная сила детерминированного подхода на Go?
В Go мы жестко разделяем «Чему равен результат?» и «Как это написано?»:

Что проверяем	Кто проверяет в Go	Результат
Арифметика и логика шага	Вычислительный модуль (big.Rat / AST)	1 + -1 == 0 → True (Шаг засчитан)
Синтаксис и культура записи	AST Linter / Правила парсера	Замечена запись + - → Предупреждение по оформлению
Формулировка подсказки	LLM (Gemini) на основе флага Go	«Отличный ответ! Только подправь скобки: 1+(−1)»
Итог
Запись 1 + -1 = 0 не ломает Go-движок. Наоборот, Go позволяет разделить сухую математическую правду и корректность математического языка.

Ребенок получает справедливую оценку: его не ругают за правильный ответ, но аккуратно обучают правильному оформлению.

1. Как Go-движок решает аналитическую и планиметрическую геометрию
В школьной геометрии (7–11 класс) 90% задач сводятся к трем типам данных: графы отношений, координаты/векторы и теоремы.

А. Граф геометрии (Geometric Scene Graph / Knowledge Graph)
Когда на канве нарисован треугольник ABC и проведена биссектриса BD, Go-движок не хранит это как «картинку». Он хранит это как граф объектов и связей:

Объекты: Точки A,B,C,D, отрезки AB,BC,AC,BD, углы ∠ABC,∠ABD,∠DBC.

Предикаты (факты):

IsTriangle(A, B, C)

OnSegment(D, A, C)

IsAngleBisector(BD, Angle(A, B, C)) ⟹∠ABD=∠DBC.

Б. Пошаговая логическая проверка (Symbolic Prover)
Когда ребенок пишет шаг доказательства: «Так как BD — биссектриса, то ∠ABD=∠DBC»:

Mathpix переводит рукописный ввод в: \angle ABD = \angle DBC.

Go-движок ищет в своем Scene Graph факты про BD.

Видит предикат IsAngleBisector и проверяет правило: «Из биссектрисы следует равенство углов».

Вердикт: CORRECT (шаг доказательства логически выведен из предыдущих условий).
