## Рамки и продукт

**R01. MVP работает на управляемых сервисах GCP, без k8s и EDA.** Сервисы запускаются в Cloud Run, данные хранятся у готовых провайдеров, своих кластеров и очередей нет. — *Почему:* быстрый выход на рынок и дешёвая инфраструктура; в простое сервис почти ничего не стоит. Платформа MathTrail на k8s (identity на Ory, Kafka/AutoMQ, infra-streaming, ArgoCD) остаётся видением на будущее. Вернуться к ней — когда вырастет нагрузка. — *Отвергнуто:* развернуть canvas-api на платформе MathTrail (Skaffold, Helm, топики `canvas.strokes` и `canvas.hints` из `contracts`). — spec 1, 19; product 4.

**R02. Рынок — международный, интерфейс сначала на английском (О-3).** Правовые режимы: COPPA (США), GDPR (ЕС) и UK GDPR с Age Appropriate Design Code (Великобритания). 152-ФЗ вне рамок: Россия не целевой рынок. — *Почему:* стек на GCP и Firebase подходит без оговорок. Для России нужна локализация персональных данных в РФ, а email родителя в Firebase её нарушает. — *Отвергнуто:* русскоязычная аудитория вне РФ; рынок РФ. — product 3; privacy 2.

**R03. В MVP входят оба пути проверки (О-1).** Путь А — арифметика и уравнения, путь Б — олимпиадные задачи-схемы. — *Почему:* решение автора. Нестандартные задачи — часть ценности продукта. — *Отвергнуто:* только путь А; путь Б за флагом для внутренних экспериментов. — product 5, 7; spec 5, 6.

**R04. В MVP две статичные задачи, по одной на путь; их добавляет автор (О-7).** Каталог, подбор задач и адаптивность откладываются на период после MVP. Формат задачи — в spec 8.6. — *Почему:* цель MVP — проверить механику холста и подсказок, а не подбор задач. — *Отвергнуто:* каталог на 100–200 задач; генерация задач LLM на лету. — product 7; spec 8.6.

**R05. В MVP нет оплаты: закрытая бесплатная бета с лимитами (О-4).** — *Почему:* сначала проверить, возвращаются ли семьи. Оплата добавляет интеграцию, налоги и возвраты. — *Отвергнуто:* подписка в MVP. — product 7, 9.

**R06. В MVP только семья: родитель и его дети (О-6).** Учителя, классы и школы появятся после MVP. Модель OpenFGA заранее описывает учителя и класс, но кортежей для них MVP не пишет. — *Отвергнуто:* роль учителя в MVP. — product 7, 14; spec 12.3.

**R07. Ребёнок занимается только на устройстве родителя, в детском режиме (О-5).** Субъект доступа — всегда родитель: запросы идут с его Firebase ID token, профиль ребёнка передаётся параметром. Ролей `student` и собственных токенов у ребёнка нет. Выход из детского режима закрыт PIN, но это барьер интерфейса, а не граница безопасности. — *Почему:* снимает противоречие черновика, где у детей нет аккаунтов, но JWT содержит `role: student`, а OpenFGA проверяет `user:student_…`. Решение проще и не требует от ребёнка учётных данных. — *Отвергнуто:* отдельная сессия ребёнка по коду или QR от родителя; она перенесена в дорожную карту. — product 6; spec 12.

**R36. После MVP — три тарифа.**
- Бесплатный — дневная квота помощи наставника, как в бете.
- За $10 в месяц — квоты больше.
- За $20 в месяц — квоты ещё больше и ИИ-наставник с голосом.

MVP остаётся бесплатной закрытой бетой (R05). Когда квота исчерпана, ребёнок решает дальше сам, без проверки (R35). — *Почему:* решение автора. — *Открыто:* размер квот и что значит «с голосом» (О-18). — product 14.

## Архитектура и инфраструктура

**R08. Стек — как в черновике.** Состав:
- canvas-api и Centrifugo на Cloud Run;
- OpenFGA — сайдкаром (R09);
- Neon Postgres, Upstash Redis;
- Firebase Auth и App Check, Mathpix;
- Gemini на Gemini Enterprise Agent Platform (бывший Vertex AI).

— *Почему:* система сразу готова к realtime и B2B; автор выбрал это осознанно (О-2). — *Отвергнуто:* минимальный вариант из одного сервиса, где подсказка приходит потоком в HTTP-ответе, а права проверяются кодом без OpenFGA; Firestore вместо Postgres. — spec 2, 3.

**R09. OpenFGA работает сайдкар-контейнером в сервисе canvas-api.** canvas-api обращается к нему по `localhost`, хранилище OpenFGA — отдельная база в том же проекте Neon. — *Почему:* нет лишнего сетевого прыжка, межсервисной авторизации и отдельного холодного старта: контейнеры стартуют параллельно (R31). Масштабируется вместе с canvas-api. Этот вариант («локальный сайдкар») упомянут в черновике. — *Отвергнуто:* отдельный сервис Cloud Run для OpenFGA. — spec 2, 12.3, 15.

**R10. SPA раздаётся с Firebase Hosting.** Клиент обращается к canvas-api и Centrifugo по их URL в Cloud Run. — *Почему:* бесплатная раздача статики с CDN и SSL в том же проекте Firebase. Документация rewrites Firebase Hosting → Cloud Run не заявляет поддержку WebSocket, поэтому на неё не рассчитываем: у Centrifugo свой адрес Cloud Run. Вариант для роста — GLB + Cloud Armor (Т-7). — spec 2, 15.

**R11. Каркас сервиса берём из mathtrail-standalone.** Переиспользуем config, logger, telemetry, apierror, Terraform для Cloud Run, devcontainer и just.
- Формат ошибок — плоский `{code, message}` из `apierror`, с необязательным полем `details`.
- `request_id` передаётся в заголовке `X-Request-Id`.

— *Почему:* каркас уже проверен в продакшене на Cloud Run, это ускоряет старт. Вложенный формат `{"error": {...}}`, описанный было в spec, не совпадал с пакетом, который мы переиспользуем. Роутер пока открытый вопрос (Т-1): в standalone gin, в черновике chi. — spec 8.3, 18.

**R12. Контракты API (proto) живут в этом репозитории, пакет `canvasapi.v1`.** Пакет `canvas.v1` в `contracts/proto` описывает будущую EDA-версию и в MVP не используется. — *Почему:* в `canvas.v1` координаты в пикселях, у точек нет времени, `user_id` — идентификатор Kratos, а семантика — события Kafka. Всё это не подходит MVP. Согласовать контракты — при возврате на платформу. — *Отвергнуто:* использовать `canvas.v1` сейчас. — spec 8, 19.

**R13. Клиент на React и Konva живёт в этом же репозитории, в `web/`.** — *Почему:* API и клиент меняются вместе, одним pull request. — *Отвергнуто:* отдельный репозиторий `ui-web`. — spec 18.

## Идентификация и доступ

**R14. Для Firebase используем Admin SDK (`firebase.google.com/go/v4`).** Через него проверяем ID token и App Check и удаляем пользователей. `golang-jwt/jwt/v5` нужен только для подписи токенов Centrifugo. `keyfunc` не используется.
- Все запросы, кроме горячего пути (штрихи и токены Centrifugo), проверяют токен с отзывом (`VerifyIDTokenAndCheckRevoked`).
- Перед `DeleteUser` вызывается `RevokeRefreshTokens`.
- Необратимые действия требуют свежего входа (`auth_time` ≤ 5 минут).

— *Почему:* Admin SDK всё равно нужен для удаления аккаунта (право на удаление), и он сам кеширует и обновляет ключи. Без проверки отзыва старый токен после удаления аккаунта мог заново создать строку `parents` и продолжить сбор данных. — *Отвергнуто:* связка `golang-jwt` + `MicahParks/keyfunc/v2` из черновика; к тому же актуальная мажорная версия keyfunc — v3. — spec 3, 12.1.

**R34. Секреты провайдеров входа — в Secret Manager, под управлением Terraform.**
- Закрытый ключ Apple и секрет клиента Google хранятся в Secret Manager.
- Сами секреты и провайдеры входа Firebase описаны в Terraform; в консоли Firebase руками ничего не настраивается.
- Значений нет в репозитории. Они приходят из секретов репозитория, и рецепт `ci-tf-apply` кладёт их в Secret Manager, если версии ещё нет. Это делается вне ресурсов Terraform — как с секретом клиента Google в mathtrail-standalone.
- Ротация — отдельная записанная команда:
  1. новое значение — сначала в секрет репозитория;
  2. затем новая версия в Secret Manager;
  3. прежняя версия уничтожается, только когда Terraform уже читает новую, — чтобы число активных версий не росло.

— *Почему:* решение автора. Полный IaC без ручных изменений в UI Firebase: воспроизводимость, прозрачный аудит IAM, удобная ротация версий.

— *Цена:*
- Значения, которые Terraform передаёт провайдерам входа, оказываются в его состоянии.
- Бакет состояния закрыт, но его читает аккаунт Terraform, а значит, и любой workflow репозитория, который входит под этим аккаунтом, — в том числе план на pull request.
- Поэтому план идёт только для веток самого репозитория: не для форков и не для PR Dependabot, чьи новые версии actions выполнились бы под этим аккаунтом до ревью. Писать в репозиторий может только автор.
- Секретов в Secret Manager становится восемь (spec 13).

— *Проверить при реализации:* умеет ли ресурс Terraform всё, что нужно входу через Apple, в том числе закрытый ключ. Если нет — вопрос автору; решение молча не меняется.

— *Отвергнуто:* настройка провайдеров в консоли Firebase вне Terraform. — spec 12.1, 13, 15.2.

## Холст и распознавание

**R15. Координаты хранятся в логической системе страницы.** Страница имеет фиксированную ширину, ось y направлена вниз, масштаб одинаков по обеим осям. Нормализация 0..1000 появляется только на границе с Gemini. — *Почему:* нормализация по ширине и высоте экрана, как в черновике, искажает картинку при других пропорциях экрана. Логические координаты не зависят от устройства. — spec 4.

**R16. Шаг решения — это строка; холст живёт на сервере и принимает дельты с `seq`.** Ластик удаляет штрихи целиком. Протокол дельт:
- приём дельты — короткая транзакция под блокировкой холста;
- повтор узнаётся по паре `seq` + `client_event_id`, и сервер возвращает сохранённый ответ из `canvas_deltas`;
- чужая дельта с занятым `seq` получает `SEQ_CONFLICT`, и клиент перенумеровывает свои;
- снимок после `RESYNC_REQUIRED` идёт с `details.expected_seq` и заменяет холст;
- на холсте не больше 300 штрихов;
- клиент не создаёт дельт, которые сервер не примет никогда;
- дневной лимит не отклоняет дельту, а только отключает проверку;
- на холст — одна проверка за раз.

Строка считается законченной, когда ребёнок перешёл к другой строке, нажал Check или 6 секунд не трогал холст. До этого ошибка в ней не показывается. Показанный маркер снимается, когда строку исправили, а строки ниже пересчитываются. — *Почему:* строка — естественная единица проверки для пути А. Удаление штрихов целиком проще для распознавания, чем «пиксельный» ластик. Дельты экономят трафик. Первая версия протокола теряла штрихи при второй вкладке, теряла проверки при сбое посреди запроса, зацикливалась на снимке и показывала ложную ошибку на недописанной строке. — *Отвергнуто:* отправлять все штрихи страницы при каждой проверке; ластик, который режет штрихи. — spec 4.3, 5.4, 8.4.

**R17. Маршрут выбирается по типу задачи, а не по ответу Mathpix.** — *Почему:* поля `is_diagram`, на котором черновик строил развилку, в ответе Mathpix нет. Тип задачи известен заранее. — spec 6.

**R18. Запрос к Mathpix v3/strokes собирается строго по документации.** Координаты — `strokes.strokes.x`/`y` как массивы массивов, без времени. В запрос добавляем `metadata.improve_mathpix: false`, на уровне аккаунта оформляем отказ от хранения данных. — *Почему:* формат черновика (`strokes.word[{x, y, t}]`) неверен. По умолчанию Mathpix хранит данные 30 дней, с отказом — удаляет в течение 24 часов. — spec 10.3; privacy 5.

**R19. Mathpix остаётся распознавателем пути А, но его обоснование проверяется спайком S1.** — *Почему:* выбор черновика — «цифровые чернила» точнее картинки на детском почерке, ответ быстрый. Экономический довод черновика при текущих ценах не держится: распознать одну строку через Gemini Flash-Lite дешевле, чем $0.002 за запрос к Mathpix (product 9). Значит, выбор держится на качестве и задержке, а их надо измерить. — *Отвергнуто без спайка:* заменять Mathpix на Gemini. — spec 6, 20.

**R20. Маркер ошибки в пути А — рамка строки по нашим штрихам. Ошибку показываем только при высокой уверенности распознавания.** Строку, распознанную неуверенно, не оцениваем. Чтобы показать ошибку, нужен более высокий порог уверенности (5.7). Пороги Mathpix отключены (`confidence_threshold: 0`), решает canvas-api. — *Почему:* Mathpix не возвращает координаты отдельных символов, поэтому якорь `"+5" → bbox` из черновика получить нельзя. Контуры строк и слов (`include_line_data`, `include_word_data`) можно попробовать для уточнения (Т-8). Уверенная ошибка распознавания (минус прочитан как плюс) иначе превращалась в ложную тревогу, а с порогом Mathpix по умолчанию наши собственные пороги ниже 0,75 не работали. — spec 4.4, 5.7, 10.3.

**R21. Путь Б для «соедини стрелками» разбирается детерминированно.** Связи определяются по концам штрихов и известной раскладке объектов слоя задачи. Рендер PNG с сеткой и Gemini vision подключаются только для неоднозначных штрихов. Роли разделены: vision-модель только распознаёт, что соединяет штрих; вердикт выносит программа по эталону; подсказку пишет текстовая модель.
- Маркер на любом маршруте — рамка самого штриха. `box_2d` модели служит только для сверки номера штриха.
- Интерпретация сохраняется и повторно модель не зовут.
- Конец штриха «между» объектами считается неоднозначным: при разнице расстояний меньше 20 единиц.
- Отдельно нарисованные наконечники отбрасываются.
- Сбой vision даёт `UNCHECKED`, а не ложную ошибку.

— *Почему:* положения объектов известны заранее, поэтому такой разбор точнее, дешевле и быстрее модели. Рамку неверной стрелки даёт штрих, а не догадка модели. Эталон не попадает в запрос с картинкой, значит, модель не может его выдать. — *Отвергнуто:* отправлять в vision-модель каждую проверку пути Б; один вызов, который сразу и распознаёт схему, и пишет подсказку (как в черновике). — spec 6.2, 6.3.

## ИИ-учитель

**R22. Модели Gemini — актуальные GA-версии с закреплённым ID.** Текстовые подсказки даёт Flash-Lite, путь Б с картинкой — Flash. Gemini 2.5 Flash не используем. — *Почему:* по release notes Vertex AI Gemini 2.5 Flash снимают 16.10.2026. Модели обновляются примерно раз в месяц, поэтому смена версии идёт через eval-набор. Конкретные ID выбираются по спайкам (Т-5). — spec 7.1.

**R23. Вердикт приходит сразу, подсказка — следом, и всё это внутри одного запроса.** Порядок работы canvas-api:
1. сразу после движка публикует в Centrifugo событие `verdict` с маркером;
2. затем вызывает LLM и публикует `hint`;
3. HTTP-ответ приходит последним и повторяет оба события на случай разрыва WebSocket.

Перед публикацией подсказки сверяется `revision` цели: подсказка к уже изменённой строке отбрасывается. Лимит выходных токенов взят с запасом, потому что токены размышлений входят в него. — *Почему:* маркер ошибки должен появиться быстрее секунды, а LLM отвечает дольше. При оплате Cloud Run за запросы CPU выделяется только на время обработки запроса, и фоновая работа после ответа почти не получает процессора. Поэтому всё остаётся внутри запроса. — *Отвергнуто:* горутина после ответа; постоянный CPU на инстансе (дороже); Cloud Tasks для подсказки (лишний компонент). — spec 7.1, 8.4, 9.4.

**R24. Если LLM не справился, выручают шаблонные подсказки; очевидные утечки ответа ловит программа.** Проверка запрещённых фрагментов работает так:
- нормализует текст, переводит числа словами в цифры, сравнивает числа отдельными токенами;
- пример третьей ступени составляет движок на числах, которые проверку не нарушат.

Лестница подсказок идёт по ключу «код ошибки + место», а не по id строки или штриха. После третьей ступени наставник предлагает позвать взрослого. — *Почему:* ребёнок всегда получает реакцию, даже при тайм-ауте, сбое или браке модели. Проверка ловит очевидные утечки, но не доказывает их отсутствие. Перефразированную утечку ловят промпт, eval-набор и ручной разбор, и доля утечек — метрика рубрики. Цвет подсветки выбирает клиент по типу действия, а не модель. — *Отвергнуто:* буквальное сравнение строк без нормализации: оно пропускало «minus five» и запрещало собственный пример третьей ступени. — spec 7.2, 7.3.

## Данные, доступ и эксплуатация

**R26. Согласие родителя подтверждает оператор, а не клиент.**
- `POST /v1/me/consent` только отмечает, что уведомление прочитано: статус `pending`.
- Статус `verified` ставит оператор командой `cmd/admin` после того, как получил подписанную форму (П-1), с методом, временем и отметкой о том, кто подтвердил.
- До `verified` профили детей и холсты не создаются.

— *Почему:* проверяемое согласие по COPPA — это не нажатие в приложении. Иначе данные ребёнка уходили бы в Mathpix и Gemini до согласия. — *Отвергнуто:* клиент сам сообщает метод согласия. — spec 8.2, 9.1, 11; privacy 6.

**R27. Удаление: сначала Neon, потом кортежи OpenFGA; повтор идемпотентен.**
- Кортежи удаляются пачками до 100, отсутствующие пропускаются.
- Аккаунт удаляется в порядке «дети → `parents` → отзыв токенов и `DeleteUser`».
- Ежедневная очистка удаляет «висящие» кортежи и таблицу `changelog` OpenFGA старше суток.

— *Почему:* при обратном порядке сбой после удаления кортежей делал повтор невозможным: `Check` отвечал 403, а данные ребёнка оставались в Neon. `changelog` OpenFGA сам не чистится и хранил бы связи «uid ↔ ребёнок» бессрочно. — spec 9.8, 11; privacy 7.

**R28. Модель OpenFGA применяет canvas-api при старте (Т-10).** Сервис находит или создаёт store `canvas`, сравнивает последнюю модель со встроенной и при расхождении записывает новую. Схему хранилища обновляет job `openfga-migrate` на образе нового релиза. — *Почему:* сайдкар слушает только localhost, и из CI до него не достучаться. Кроме того, ID модели появлялся бы уже после выкладки сервиса. — *Отвергнуто:* `fga model write` в CI; ID store и модели в конфигурации. — spec 12.3, 15.5.

**R29. Доступ в бету — по одноразовым инвайт-кодам (О-11).** В Neon хранится SHA-256 кода, при первом входе код привязывается к uid. Email canvas-api не читает. — *Почему:* список email ломается на Apple «Hide My Email», где в токене случайный адрес. А несолёные хеши email в публичной конфигурации позволили бы проверить, чья семья участвует в бете. Коды — не персональные данные. — *Отвергнуто:* allowlist email или их хешей в конфигурации. — spec 8.2, 12.1; product 6.

**R30. Проверка здоровья — `GET /health`, не `/healthz`.** — *Почему:* Google Front End в Cloud Run перехватывает пути, которые заканчиваются на `z`. mathtrail-standalone на это уже наткнулся (его R34). — spec 8.2, 15.

**R31. Порядок выкладки — как в mathtrail-standalone.** Шаги:
1. `terraform apply` (образы Terraform игнорирует);
2. сборка образов;
3. миграции — jobs на новом образе;
4. новая версия сервисов;
5. Hosting;
6. smoke-проверка `/health`.

Контейнеры сервиса стартуют параллельно, startup probe сайдкара срабатывает каждую секунду. — *Почему:* при миграциях до `terraform apply` jobs работали на старом образе, а первый прогон падал без registry. Последовательный старт с probe по умолчанию растягивал холодный старт примерно до 11 с. — spec 14.2, 15.

**R32. В MVP одна среда — prod; вторая (dev) создаётся после успешного MVP.** Один проект GCP со своим проектом Firebase. Каждый мерж в `main` выкатывается в prod конвейером из R31. Когда MVP состоится, заводим вторую среду: отдельные проекты GCP и Firebase, тот же Terraform со своим `*.auto.tfvars`. — *Почему:* решение автора при составлении плана реализации (RUN.md).
- Главный довод — ручная настройка. Одна среда вдвое сокращает её: проект, Firebase, Neon, Upstash, секреты.
- Стоимость второй среды невелика, но не нулевая: её секреты целиком выходят за бесплатный лимит (расчёт — spec 13), а бесплатные лимиты платёжного аккаунта делились бы на ещё одного потребителя (spec 14.4).
- Конвейер «мерж — выкладка в prod» уже работает в mathtrail-standalone (его R32).
- Prod до публичного запуска защищают:
  - обязательные проверки CI на pull request;
  - выкладка только после зелёного CI этого коммита и только из `main` (R33);
  - smoke-проверка после выкладки;
  - откат на прошлый образ по digest. Он безопасен, потому что миграции совместимы с кодом прошлого релиза: «сначала добавить, потом убрать» (spec 15.5).

  В закрытой бете участвуют знакомые семьи.

— *Отвергнуто:* dev и prod с первого дня (первая редакция spec 15.1); выкладка `main` в dev, а релиза — в prod после ручного одобрения. — spec 8.1, 13, 14.4, 15.1, 15.5; product 9.

**R33. Выкладка в prod — только после зелёного CI и только из `main`.**
- Задания CD зависят от CI (`needs: [ci]`): выкладка начинается, только когда все проверки CI этого коммита прошли.
- Автоматический запуск — мерж в `main`. Ручная кнопка запуска тоже работает только на `main`.

— *Почему:* решение автора. Среда одна — prod (R32). Выкладка с произвольной ветки или параллельно с CI прямо грозит выкатить сломанный код и невалидные миграции: jobs миграций работают на новом образе до новой версии сервиса (R31). — *Отвергнуто:* как в mathtrail-standalone — CD по `push` в `main` параллельно с CI и ручной запуск из любой ветки (его R30 и R32). — spec 15.5; R31, R32.

**R35. Исчерпанный дневной лимит не прерывает занятие: ребёнок решает дальше сам, без проверки.**
- Холст работает как обычно, штрихи сохраняются.
- До обновления лимита строки не распознаются и не проверяются: `UNCHECKED` с причиной `limit`, без вызовов Mathpix и Gemini.
- Наставник молчит: ни маркеров, ни подсказок, ни поздравления с решённой задачей.
- Ребёнку об этом сказано мягко и один раз за сеанс: «I've helped all I can for now. Keep going on your own!». По Check фраза повторяется. Времени она не обещает: сутки лимитов — UTC, и для семьи в США они кончаются ещё днём.
- Когда лимит обновится, следующая проверка — по паузе или по Check — начнёт с непроверенных строк, сверху вниз.

— *Почему:* решение автора. Ребёнка не прогоняют с листа: он может дописать решение сам. Проверка останавливается целиком, а не только подсказки, и это экономит главное — распознавание Mathpix (70–80% стоимости, product 9). — *Отвергнуто:*
- фраза «That's enough practice for today — see you tomorrow!»: она предлагала закончить занятие;
- проверка с рамками, но без вопросов наставника;
- проверка с шаблонными вопросами вместо модели.

— spec 5.4, 8.4, 14.5; product 5.6, 9.
